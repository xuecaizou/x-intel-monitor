图 1 · 总体分层架构

四个层次自上而下：客户端 → FastAPI 服务 → 引擎管道 → 数据与外部依赖。所有外部访问（浏览器、Agent、推送目标）都经 REST API，内部组件单进程协作。

关键机制

  1. 三级降级抓取：A syndication（免登录但匿名额度易 429）→ B Nitter RSS（实例缓存直连 + twiiit 轮换发现，按「<?xml 开头」验收防 CF/Anubis 挑战页）→ C Cookie 直连（实验性）。任一层成功即止，全失败才整体标红。
  2. 增量短路：kv 记录每账号已入库的置顶雪花 id；新一轮 RSS 仍会整体拉取（X 无条件拉取接口），但会在置顶 id 处截断——无更新时 0 入库、0 AI、0 推送。
  3. 排序与时区：雪花 ID 全局时间有序，列表按 CAST(tweet_id AS INTEGER) DESC 排序，补抓批次内不乱序；published_at 存 GMT 裸值，前端按 UTC 解析转本地时区显示。
  4. AI 额度保护：自动阶段每轮限 auto_limit 条；研判失败的推文标 ai_status=error 不自动重试；无地理信息的推文标「未知」不被补标任务反复处理。
  5. 模拟模式：通道凭据留空 = 模拟——消息照常经模板生成并写入推送日志（标「模拟成功」），不外发；填入凭据即真实推送，无需重启。
  6. 媒体代理：/api/media?url=… 服务端经抓取代理拉取 pbs.twimg.com 原图（域名白名单校验），客户端无需直连 X 图片 CDN，并带 24h 缓存头。
  7. 通道多实例：channels.{key}.instances 列表（每实例 name/凭据/enabled/filters 四维筛选），旧单实例结构运行时兼容读取；推送按实例循环——全局过滤后每实例再过自己的 filters，推送日志 channel 列记「类型·实例名」；企微 45009 限频自动退避（15s/30s×3 次）+发送节奏 4s。
  8. 推送门控：AI 实时开启时，仅 ai_status='ok' 的推文进入推送（失败重试 2 轮后附错误说明放行）——保证推送内容必经研判；推送后标记 pushed 防重复。
  9. 混合分类：16 类情报分类采用 脚本规则（9 组关键词零成本命中）+ AI 批量兜底（每 10 条一次调用）双通道；新推文研判时顺带标注分类。
  10. syndication 熔断：连续 3 轮失败后 30 分钟内跳过该层（省每轮 15s+ 无效等待），成功自动复位。
  11. 报告任务桥接：系统只做任务管理与验收（建任务/线索包落盘/claim 原子领取/复跑机械门禁/推送），报告正文由外部 report-writer Agent 产出——验收不信任 Agent 自报 gate 结果，系统必须自己复跑已配置的门禁脚本（py -3.13 subprocess，exit 0=已交付待推，否则待人工，宁拦住不放过）；推送按通道能力分发（企微附件两步法，其余通道摘要+内网获取提示）。
  12. AI 模型拉取：GET {base_url}/models（OpenAI 兼容标准端点）→ 前端 datalist 下拉，仍可手输；先保存配置再拉取，保证用最新地址与 Key。
